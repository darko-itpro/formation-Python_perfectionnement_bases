10  L’héritage multiple

Python est un des rares langages modernes qui permette l’héritage multiple. Cela signifie qu’une classe peut spécialiser plusieurs classes.

Un grand principe de l’héritage multiple est… de l’éviter au maximum.

L’héritage multiple s’est révélé problématique ce qui a conduit la plupart des langages à s’orienter vers de l’héritage simple et à ajouter le concept d’interfaces. Dans cette partie, nous allons voir les principaux problèmes que nous pouvons rencontrer.

10.1 Modèle de travail

Le modèle es la partie employés d’un centre de formation reprenant celui de la partie précédente. Nous avions nos objets représentant des salariés et des prestataires. Nous avons spécialisé les salariés en commerciaux (SalesEmployee) et formateurs (salariés) (Coach).

L’implémentation des SalaryEmployee et DailyEmployee est la suivante :

En effet, nous ne voyons pas dans les classes au premier niveau que ces deux classes ont en fait un ancêtre commun.

10.2 L’ordre de résolution des méthodes

Lorsque qu’une méthode ou un attribut d’une classe est accédé, Python utilise son MRO (Method Resolution Order) pour le retrouver.

Une classe possède l’attribut spécial __mro__ qui va retourner l’ordre dans lequel Python recherchera les attributs. Cet ordre est celui qui est respecté lorsque vous appelez la fonction super(). Dans le cas de DailyCoach, l’attribut retourne le résultat suivant.

In [1]: DailyCoach.__mro__
Out[1]: 
(pyacademy.people.DailyCoach,
 pyacademy.people.Coach,
 pyacademy.people.SalaryEmployee,

 pyacademy.people.Employee,
 abc.ABC,

Lorsque nous créons une nouvelle instance, la méthode __init__() de DailyCoach est appelée ensuite celle de Coach puis celle de SalaryEmployee puis DailyEmployee et ainsi de suite.

10.3 Résolution du problème des paramètres

Si dans certains cas, appeler l’ensemble des méthodes sera ce que vous souhaitez, dans d’autres, vous ne le souhaiterez pas.

Dans nos exemples, le constructeur est un premier problème qui peut être résolu en appelant spécifiquement la méthode du parent souhaité.

class DailyCoach(Coach, DailyEmployee):
    def __init__(self, first_name: str, last_name: str,
                 id: int, daily_rate: float):
                 
        DailyEmployee.__init__(self, first_name, last_name,
                               id, daily_rate)

Cependant, nous aurons à nouveau le problème lors de l’appel à .calculate_payroll(). Dans notre cas, il faudra à nouveau faire appel à l’implémentation spécifique.

10.4 Les mixins

Les mixins sont un moyen d’exploiter l’héritage multiple pour proposer un code réutilisable à la frontière entre les interfaces et les classes abstraites sans forcer à une hiérarchie rigide.

Une mixin est une classe qui va répondre à certaines conventions :

  • Un nom destiné à éviter toute ambiguïté.
  • Ce sont des classes simples qui réalisent un comportement. Elles n’ont pas de généralisation.
  • Elles n’ont qu’une seule responsabilité
  • Elles n’ont pas d’état donc rarement un constructeur ou des attributs d’instance;
  • Elles sont destinées à étendre le comportement d’autres classes et n’ont aucun sens par elles-même.

Un exemple de mixin peut être :

class SerializableMixin:
    def serialize(self) -> dict:
        if hasattr(self, "__slots__"):
            return {
                name: getattr(self, name)
                for name in self.__slots__
            }
        else:
            return vars(self)

Django utilise intensivement les mixins pour étendre les comportements. Vous pouvez voir un exemple pour la validation du login : https://docs.djangoproject.com/en/5.2/topics/auth/default/#the-loginrequiredmixin-mixin ## Héritage multiple, conclusion

L’héritage multiple est source de nombreux problèmes, il est donc fortement déconseillé de l’utiliser. De manière générale, l’héritage est déconseillé en faveur de la composition. Il y a cependant une différence d’interprétation. L’héritage signifie est un alors que la composition signifie contient/comporte un. Nous pouvons le voir avec la modélisation d’une formation et plus spécifiquement une session de formation qui a lieu à une certaine date et à un certain lieu avec des stagiaires. Une formation (au sens sujet et contenu) n’est pas une liste, ce n’est pas non plus un lieu. Une session n’est pas non plus une formation (au sens sujet et contenu) ni un lieu. Par contre, une session comporte un sujet et un lieu.

Cependant, dans un langage déclaratif, il faut associer un type à nos classes pour informer le langage de ce que peut faire l’objet. Ces langages ont ajouté la notion d’interfaces. Une interface est un contrat déclarant ce que peut faire l’objet (c’est une liste de méthodes).

En Python, les interfaces sont inutiles. Les méthodes sont implémentés en fonction du besoin et les programmes n’ont pas besoin de connaitre ce que sont les objets (leur type) mais ce qu’ils peuvent faire (leurs méthodes).
