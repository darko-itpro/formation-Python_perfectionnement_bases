14  Introduction à threading

Créer un thread se fait par la création d’un objet de type threading.Thread().

La signature de la classe est la suivante (tous les paramètres ne sont pas représentés) :

threading.Thread(target=None, args=(), kwargs={}, daemon=None)

Les arguments doivent être nommés.

  • target : objet callable qui sera appelé lors de l’exécution du thread
  • args : séquence d’arguments positionnels pour l’appel du callable
  • kwargs : séquence d’arguments nommés pour l’appel du callable
  • daemon : Définit explicitement si le thread est détaché du fil courant.

Pour illustrer, nous allons nous utiliser des actions longues et pour cela simplement mettre l’exécution du code en attente. Pour l’observer, nous utiliserons un logger.

Nous allons utiliser (et donc importer) les bibliothèques logging, threading et time.

def thread_function(name):
    logging.info(f"Thread {name} started")
    time.sleep(2)
    logging.info(f"Thread {name} finished")

Nous pouvons créer un thread pour avec cette fonction. Pour exécuter ce thread, il suffit de faire un appel à la méthode Thread.start().

logging.info("Main    : before creating thread")
x = threading.Thread(target=thread_function, args=(1,))
logging.info("Main    : before running thread")
x.start()
logging.info("Main    : wait for the thread to finish")
logging.info("Main    : all done")

Si vous exécutez ce programme, vous verrez qu’il se termine avant le thread.

14.1 Les threads en tant que daemon

En informatique, un daemon est un processus qui s’exécute en tâche de fond.

Pour threading, un daemon est un thread qui sera arrêté à la fin du programme, qu’il ai terminé son exécution ou non.

Ainsi, si vous complétez la déclaration du thread de la manière suivante :

x = threading.Thread(target=thread_function, args=(1,), daemon=True)

Vous ne verrez pas l’affichage du dernier log.

14.2 Synchroniser les thread

La méthode .join() de l’objet thread fait attendre au fil principale la fin de l’exécution du thread.

Insérée dans le code précédent, le programme s’arrête le temps que le thread se termine.

x.start()
logging.info("Main    : wait for the thread to finish")
x.join()
logging.info("Main    : all done")

14.3 Travailler avec plusieurs threads

Si vous exécutez plusieurs threads à partir d’un même thread principal, vous verrez que, potentiellement, les exécutions peuvent se croiser. Un thread peut, pour la même exécution, se terminer avant un autre thread démarré avant.

C’est le système qui détermine quel thread faire avancer. Vous n’avez pas de moyen d’anticiper quel thread le système fera avancer.

Si les threads sont indépendants, il n’y a pas vraiment de conséquence. Par contre, nous pouvons avoir à faire face à des race conditions.

14.4 Les race conditions

Une race condition se traduit par situation de compétition ou situation de concurrence. Il s’agit de concurrence d’accès à une ressource.

L’illustration suivante montre le problème de gestion d’un compteur. Le compteur est géré par la classe suivante.

class SomeService:
    def __init__(self):
        self.value = 0

    def update(self, name):
        logging.info(f"Thread {name}: starting update")
        local_copy = self.value
        local_copy += 1
        time.sleep(0.1)
        self.value = local_copy
        logging.info(f"Thread {name}: finishing update")

Dans notre programme principal, nous aurons un seul service. Puis, nous allons déclencher deux threads qui mettent à jour le compteur.

service = SomeService()

t1 = threading.Thread(target=service.update, args=(1,))
t2 = threading.Thread(target=service.update, args=(2,))
logging.info(f"Testing update. Starting value is {service.value}.")
t1.start()
t2.start()
t1.join()
t2.join()
logging.info(f"Testing update. Ending value is {service.value}.")

 Les logs correspondant sont présentés ci-dessous, la valeur finale de 1 aurai dû être à 2.

Testing update. Starting value is 0.
Thread 1: starting update
Thread 2: starting update
Thread 1: finishing update
Thread 2: finishing update
Testing update. Ending value is 1.

Nous allons avoir besoin de synchroniser nos threads et une manière élémentaire pour le faire est de créer un verrou.

14.4.1 Synchronisation avec lock

Un verrou agira comme un totem. Il ne peut être possédé que par un seul thread. Pour qu’un autre thread puisse l’avoir, il faut que le précédent le restitue.

Pour cela, les méthodes de base sont .acquire() et .release(). Si un thread fait appel à .acquire() mais que le lock n’est pas disponible, il attendra jusque’à sa libération. 

Les verrous peuvent être utilisés comme un context manager.

Notre classe devient le code ci-dessous.

class SomeService:
    def __init__(self):
        self.value = 0
        self._lock = threading.Lock()

    def update(self, name):
       with self._lock:
            local_copy = self.value
            local_copy += 1
            time.sleep(0.1)
            self.value = local_copy

Si vous ajoutez du log autour du context manager, vous verrez que le second thread commencera l’appel à la méthode avant la fin de l’exécution du premier thread. Mais il sera bloqué avant le contexte manager tant que le premier thread n’a pas relâché ce lock.

Ceci permet de résoudre le problème d’accès concurrent aux ressources partagées entre les threads.

14.4.2 Deadlock

Le lock amène un autre problème : deux threads peuvent se bloquer mutuellement. C’est le principe des deux coffres dans lesquels sont enfermées les clefs pour ouvrir l’autre. C’est une situation de deadlock.

Un deadlock survient communément dans une des deux situations suivantes :

  • Un bug d’implémentation où le lock n’est pas libéré proprement
  • Un design où la fonction a besoin d’être appelée par une fonction qui peut avoir ou non un lock. Cette situation arrive habituellement dans les situations d’appels récursifs.

Pour éviter la première situation, préférez la syntaxe avec le contexte manager.

Pour la seconde, Python propose un second objet, RLock. Il permet à un même thread d’acquérir un même lock plusieurs fois avant de le libérer. Cette classe est conçue pour les cas des appels récursifs.

En dernier recours, vous avez l’option du paramètre timeout de la méthode .acquire(). L’argument doit être un réel correspondant à un nombre de secondes.

14.5 Limiter le nombre de threads avec les sémaphores

Le sémaphore est une des plus anciennes primitives de synchronisation conçue par l’informaticien Edsger W. Dijkstra. Un sémaphore est initialisé avec un compteur et expose deux  méthodes : .acquire() et .release().

Edsger W. Dijkstra avait défini pour les sémaphores les opérations Init, P et V. P et V viennent du néerlandais Proberen et Verhogen qui signifient respectivement Sonder et incrémenter.

Un appel à la méthode .acquire() décréments le compteur. Un appel à la méthode .release() incrémente le compteur.

Un appel à .acquire() lorsque le compteur est à 0 bloquera le thread qui a fait cet appel jusque’à ce qu’un autre fasse appel à .release().

La valeur passée à l’initialisation n’est pas un maximum. Il est possible de faire appel à .release() alors que le sémaphore est à cette valeur et donc l’augmenter. La classe threading.BoundedSemaphore est identique à threading.Semaphore mais empêche que le compteur excède sa valeur initiale.

Les sémaphores sont utilisés pour limiter le nombre d’utilisation simultanée d’une ressource comme par exemple l’accès à une base de données.

C’est également la solution au problème du diner des philosophes

14.6 Spécialiser les Threads

La classe threading.Thread peut être spécialisée avec l’héritage. Mais pour le faire correctement, il est indispensable de connaitre le fonctionnement d’un objet Thread.

Dans les exemples précédents, nous avons fait appel, pour démarrer le thread, à la méthode Thread.start(). Cette méthode crée un nouveau thread et appelle la méthode Thread.run().

Lorsque nous consultons le code source de cette méthode, nous avons (documentation omise) :

def run(self):
    try:
        if self._target is not None:
            self._target(*self._args, **self._kwargs)
    finally:
        del self._target, self._args, self._kwargs

Cette méthode appelle donc le callable passé en argument à la création de l’objet en lui passant en argument les éléments de args et kwargs.

Vous comprenez donc que vous pouvez créer plus spécifiquement un thread qui ne recevra pas de callable mais aura directement le code dans la méthode .run().

Créer son propre thread consiste donc à spécialiser cette classe et à surcharger le constructeur et la méthode .run(). Vous ne devriez pas surcharger une autre méthode. Cependant, vous pouvez, et c’est pourquoi vous créerez vos propres threads, ajouter d’autres méthodes.
