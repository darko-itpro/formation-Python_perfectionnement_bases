19  Structure de projet Python

Deux approches de référence pour organiser un projet Python selon son usage : la proposition de Kenneth Reitz (projets applicatifs) et la structure src-based (packaging et distribution).

19.1 Structure proposée par Kenneth Reitz

Popularisée par le guide The Hitchhiker’s Guide to Python, cette structure convient aux projets applicatifs, scripts, outils CLI et services web. Elle privilégie la lisibilité et la convention sur la configuration.

mon_projet/
1+-- mon_projet/
|   +-- __init__.py
2|   +-- __main__.py
|   +-- core.py 
|   \-- ...
|
3+-- tests/
|   +-- __init__.py
|   +-- test_core.py
|   \-- ...
|
4+-- docs/
|   +-- conf.py
|   \-- index.rst
|
5+-- .env.example
+-- .gitignore
6+-- LICENSE
7+-- Makefile
8+-- README.md
9+-- requirements.txt
10+-- requirements-dev.txt
11\-- pyproject.toml
1
Package principal, vous ne devez théoriquement avoir qu’un seul package pour votre projet principalement pour imposer un namespace.
2
Pour rappel, un fichier __main__.py est le point d’entrée en exécutant le module (ici par un python -m mon_projet)
3
Le package de tests isolés du code métier.
4
Documentation (Sphinx, MkDocs…).
5
Optionnel, variables d’environnement (modèle).
6
Il est recommandé de toujours préciser la licence d’utilisation.
7
Spécifique au monde Posix et à l’outil make pour automatiser les tâches courantes (test, lint, run…).
8
Le README.md doit présenter le projet et indiquer comment configurer l’environnement de dev.
9
Dépendances runtime
10
Dépendances de développement
11
Optionnel, norme récente pour centraliser les métadonnées (PEP 621)

19.1.1 Principes clés

  • Le package applicatif est à la racine du dépôt, directement importable après pip install -e .
  • tests/ est un répertoire de premier niveau, séparé du package
  • Pas de sous-dossier src/ : le code est découvrable sans configuration supplémentaire
  • Adapté aux projets Django, Flask, FastAPI, scripts de data science, outils internes

19.1.2 Exemple d’import

# Après pip install -e .
from mon_projet.core import MaClasse

19.2 Structure src-based

Recommandée par PyPA et adoptée comme bonne pratique pour les bibliothèques distribuées sur PyPI. Elle isole le code source dans un répertoire src/ afin d’éviter les importations accidentelles depuis la racine du projet lors des tests.

mon_projet/
+-- src/
1|   \-- mon_projet/
|       +-- __init__.py
|       +-- __main__.py
|       +-- core.py
|       \-- ...
|
2+-- tests/
|   +-- conftest.py
|   +-- test_core.py
|   \-- ...
|
+-- docs/
|   \-- ...
|
+-- .gitignore
+-- LICENSE
+-- README.md
3+-- pyproject.toml
4+-- requirements.txt
\-- requirements-dev.txt
1
Package installable
2
Tests à la racine, séparés du package source
3
Configuration unique (build, deps, outils)
4
La présence des requirements est destiné aux devs (de manière historique)

19.2.1 pyproject.toml minimal

À titre d’exemple, voici le contenu d’un fichier pyproject.toml minimal qui référence setuptools.

[build-system]
requires = ["setuptools >= 77.0.3"]
build-backend = "setuptools.build_meta"

[project]
name = "mon-projet"
version = "0.1.0"
description = "Description courte du projet"
readme = "README.md"
requires-python = ">=3.11"
license = { file = "LICENSE" }
dependencies = [
    "httpx>=0.27",
]

[project.optional-dependencies]
dev = [
    "pytest>=8.0",
    "ruff>=0.4",
]

19.2.2 Principes clés

  • Le code dans src/ n’est pas importable sans installation préalable (pip install -e .), ce qui garantit que les tests exercent bien le package installé et non les fichiers locaux bruts
  • Un seul fichier de configuration : pyproject.toml (remplace setup.py, setup.cfg, MANIFEST.in)
  • tests/ reste en dehors de src/ pour ne pas être inclus dans la distribution
  • Adapté à la publication sur PyPI, aux bibliothèques réutilisables, aux projets open source

19.2.3 Installation en mode éditable

pip install -e ".[dev]"
